## 0. 文档定位

本文件不是重新定义产品需求，而是把已经确认的产品方案转换为 Codex 可以稳定执行的开发边界、顺序、默认技术决策、交付格式和停止条件。

开发时必须同时提供以下两份文件：

1. `日本资格考试数据媒体_完整产品设计方案.md`：产品范围、事实可信链、页面职责、数据模型、SEO、AdSense 和最终验收的唯一需求基线。
2. `Codex_开发交接与启动说明.md`：Codex 的执行顺序、工程约束、阶段交付、验证证据和沟通方式。

如果两份文档出现冲突：

- 产品范围、数据真实性、页面职责和验收指标，以产品设计方案为准。
- 开发顺序、首轮范围、停止条件和交付格式，以本交接说明为准。
- 不允许 Codex 自行选择一个看似合理的答案覆盖冲突；必须记录冲突并请求确认。

## 1. 是否可以直接开发

可以开始开发，但不能用一句“按文档全部开发”要求 Codex 一次性完成整个项目。

原因：本项目同时包含公开网站、后台、数据库、采集器、解析器、审核状态机、对象存储、SEO、日历、比较工具和监控。一次性执行会导致以下风险：

- 在数据契约冻结前先写页面，后续大面积返工。
- 将示例日期、费用或合格率误写成真实生产数据。
- 为了快速出页面而绕过候选事实、审核和版本链。
- 同时改动过多文件，难以验证错误来自哪个模块。
- Codex 遇到未确定的部署、认证或密钥问题后自行假设。

正确方式是：每次只启动一个阶段或一个可独立验收的子任务，验收通过后再继续下一阶段。

## 2. 已冻结的产品边界

### 2.1 首发资格

首发只能覆盖以下 6 个资格：

1. 宅地建物取引士（`takken`）
2. 行政書士（`gyoseishoshi`）
3. ITパスポート（`it-passport`）
4. 基本情報技術者（`fundamental-it-engineer`）
5. 日商簿記（`bookkeeping`）
6. FP技能検定（`fp`）

阶段 1 只实现宅建和 ITパスポート，用于分别验证传统年度考试与 CBT/动态公告两类数据场景。

社会保険労務士和中小企業診断士不是首发范围，不得提前加入。

### 2.2 首发不做

- 登录、个人中心、普通用户账户和收藏同步。
- 邮件订阅、推送提醒和营销自动化。
- 课程交易、题库收费、会员系统。
- 评论、论坛、问答社区。
- 主观难度星级、收入排名、推荐排行榜。
- 海外资格数据和多语言站。
- 大规模 AI 文章生成。
- 未经确认的“日本专家监修”、作者身份、用户评价或亲身经历。

### 2.3 核心业务链不得缩减

```text
官方来源
→ 原始快照
→ 结构化候选事实
→ 规则校验、冲突检测和风险分级
→ 自动批准或异常审核
→ 正式事实与版本历史
→ 页面/API统一读取
→ 受影响页面同步更新
→ 质量监控和纠错反馈
```

不能为了快速上线而让采集器直接写正式事实表，也不能让前端直接读取候选事实。

## 3. Codex 开工前必须完成的只读检查

Codex 收到任务后，必须先检查项目，而不是立即创建或修改文件。

### 3.1 仓库检查

依次检查：

```text
AGENTS.md 或同类仓库指令
README 与 docs
git status、当前分支、最近提交和远程仓库
目录结构
package.json、锁文件、Python 配置和现有依赖
.env.example 与配置加载方式
数据库迁移和 schema
测试、Lint、类型检查、构建和 CI
部署配置和已有基础设施
```

### 3.2 检查结果分类

Codex 必须给出以下结论之一：

- `现有仓库可继续开发`：沿用当前结构和技术栈。
- `现有仓库需要最小调整`：列出必要调整，禁止无关重构。
- `空仓库/新项目`：按本文件的默认技术栈初始化。
- `存在阻塞`：说明缺少的决定、权限、文件或运行环境，停止相关实现。

### 3.3 保护现有工作

- 不覆盖用户已有的未提交改动。
- 不使用 `git reset --hard`、强制检出或批量删除。
- 不修改与当前阶段无关的代码。
- 不提交密钥、Cookie、访问令牌、生产数据库地址或对象存储凭据。
- 如果发现工作区不干净，先列出与本任务重叠的文件，再决定如何继续。

## 5. 必须优先冻结的数据契约

在编写正式页面前，必须先冻结以下内容：

1. 资格、机构、级别、来源和别名主数据。
2. 候选事实、正式事实、事实修订、审核任务和变更事件的数据结构。
3. 状态枚举、风险枚举和事件类型枚举。
4. 动态事实的公开 API 响应结构。
5. UTC、JST、日期型字段和时间型字段的使用规则。
6. 多等级、多实施机构和 CBT 场景的建模方式。
7. 事实到受影响页面的依赖关系。

### 5.1 动态事实最小字段

每个正式动态事实至少包含：

```text
qualification_id
exam_level_id（允许为空）
exam_year
fact_key
value_type
normalized_value
display_value
status
risk_level
source_id
source_snapshot_id
official_published_at
retrieved_at
verified_at
valid_from
valid_to
current_revision_id
```

### 5.2 禁止放入种子数据的内容

以下信息不得因为出现在需求文档、接口示例或测试说明中，就被写入生产种子数据：

- 任何具体考试日期。
- 任何具体报名起止日期。
- 任何具体费用。
- 任何具体合格率、合格人数或合格点。
- 尚未通过采集、快照、校验和审核链的制度说明。

测试需要这些数据时，只能使用带有 `fixture`、`synthetic` 或 `test-only` 标记的虚构数据，并确保生产构建不会读取测试夹具。

## 6. 关键实现规则

### 6.1 权限与数据流

- 采集器：只能写快照和候选事实。
- 验证/审核服务：可以批准候选并生成事实版本。
- 发布服务：根据已批准事实生成公开版本和重建事件。
- 公开网站：只读正式事实和公开来源信息。
- AI：只能读取已批准事实，不得写候选或正式事实。

本地开发可以共享一个 PostgreSQL 实例，但必须通过独立数据库角色或明确的 repository/service 边界模拟最小权限。

### 6.2 幂等性

- 相同来源、快照哈希、事实键和适用年度重复运行时，不得重复生成候选事实。
- 同一个候选事实重复批准时，不得产生多个当前版本。
- 发布和页面重建任务必须可安全重试。
- Webhook、Cron 和队列任务必须包含幂等键。

### 6.3 页面变化与事实变化分离

```text
页面哈希未变化 → 记录检查成功，不生成候选
页面哈希变化但目标字段未变化 → 保存快照，不更新用户正文
目标字段变化 → 生成候选并进入风险判断
```

导航、页脚、版权年份、CSS 或脚本变化不能生成考试信息更新。

### 6.4 高风险强制审核

以下字段和事件不得自动批准：

- 考试日期和报名截止。
- 费用和支付要求。
- 报考资格。
- 考试科目、方式和合格标准。
- 延期、中止、休止、灾害、会场变更和制度变更。
- OCR 才能读取的候选。
- 新旧官方来源冲突。
- 来源 404 或异常重定向。

### 6.5 原子发布

事实批准必须产生完整事务：

1. 创建新事实修订。
2. 关闭旧修订有效期。
3. 更新当前事实指针。
4. 创建变更事件。
5. 计算受影响页面。
6. 触发构建或缓存失效。
7. 构建成功后切换公开版本。

构建失败时继续提供上一正确版本，并生成告警。禁止出现首页已经更新、详情页仍是旧数据的状态。

### 6.6 页面日期语义

- `published_at`：页面首次公开时间。
- `updated_at`：页面可见内容最后一次真实变化。
- `official_verified_at`：最后成功检查官方来源的时间。

采集任务成功但事实未变化时，不得修改 `updated_at`。

### 6.7 ICS

- 不要求登录或邮箱。
- 相同资格、年度和事件使用稳定 UID。
- 日期变化后增加 `SEQUENCE`。
- 明确使用 JST，避免客户端时区偏移。
- 取消或延期事件应按 ICS 规范反映状态，不生成一个无关联的新事件。

## 7. 分阶段执行与验收

## 7.1 阶段 0：项目基础与规则冻结（首轮只做本阶段）

### 目标

建立可以继续开发的数据和工程骨架，不连接生产环境，不批量采集真实数据，不建设完整页面。

### 必须交付

- 仓库现状审计结果。
- 单仓目录和运行说明。
- `.env.example`，只包含变量名和安全说明。
- 本地 PostgreSQL 和对象存储配置。
- 首发 6 个资格的主数据与别名；不得包含未验证动态事实。
- 机构、来源登记、快照、候选事实、校验、冲突、审核、正式事实、修订和变更事件 schema。
- 状态、风险、事件类型和事实键枚举。
- 数据迁移和开发种子脚本。
- 公开 API 与内部写入接口的契约草案。
- `apps/web`、`apps/admin` 和 `services/api` 可运行骨架。
- Python 采集/解析包骨架和适配器接口。
- 至少一组纯测试夹具，清楚标记为非真实数据。
- 核心权限、幂等和高风险审核的单元测试。
- CI 基线。
- ADR：技术栈、时间处理、事实版本模型、模块权限边界。

### 阶段 0 不允许做

- 将需求文档中的示例数值写成真实数据。
- 编写 52 个正式页面。
- 连接生产数据库、生产对象存储或正式 AdSense。
- 实现 6 个机构的完整采集器。
- 绕过 schema 先把信息写进静态 JSON 或页面源代码。
- 为了展示效果伪造官方确认状态。

### 阶段 0 验收

```text
全新环境能按 README 启动
迁移可从空数据库执行成功
种子数据重复运行不重复插入
公开 API 不返回候选事实
高风险候选不能自动批准
未绑定来源快照的候选不能批准
重复批准具备幂等保护
TypeScript 类型检查通过
Python 与 TypeScript 单元测试通过
前端与后台骨架可构建
CI 配置能够执行上述检查
```

## 7.2 阶段 1：宅建与 ITパスポート完整闭环

只有阶段 0 验收通过后才能启动。

### 必须交付

- 两个资格的官方来源登记。
- 独立适配器和历史快照回归夹具。
- HTML/公告解析、候选事实、校验、风险和审核。
- 原始快照可回溯。
- 审核队列可查看新旧值、原文、来源和校验结果。
- 批准、拒绝、延后、官方确认中和回滚。
- 公开网站基础导航、首页、资格目录。
- 两个资格各 5 类页面模板。
- 年度日历、来源展开和信息状态组件。
- 一次事实批准后所有引用页面同步。

### 阶段 1 必测场景

1. 页面哈希变化但目标事实不变。
2. 考试日期发生变化并被识别为高风险。
3. 官方来源冲突。
4. 适配器结构失效。
5. 来源返回 404。
6. 批准后页面同步。
7. 构建失败后仍展示上一正确版本。
8. 事实回滚后页面恢复一致。

## 7.3 阶段 2：扩展到 6 个资格和跨资格工具

新增行政書士、基本情報技術者、日商簿記和 FP技能検定，并支持多等级、多实施方式和多机构场景。

交付范围：

- 4 个新增资格适配器。
- 6 个资格完整数据页面。
- 资格比较、费用、合格率、更新中心。
- 单事件和全年 ICS。
- 4 篇通用指南。
- 约 52 页的有效首发规模；没有足够已验证数据时不得建立空页面。

## 7.4 阶段 3：SEO、AdSense 与上线准备

交付范围：

- Sitemap、robots、canonical 和结构化数据。
- 参数筛选页 noindex。
- GSC 和分析埋点。
- Core Web Vitals 优化。
- AdSense 代码接入与排除区域。
- 隐私、条款、广告、AI、来源、编辑和订正页面。
- 日文模板母语校对结果回写术语表。
- 生产备份、监控、告警和回滚演练。

## 7.5 阶段 4：稳定运营与扩展评估

只有满足以下条件才讨论新增资格：

- 自动提取成功率 ≥95%。
- 高风险变化拦截率 100%。
- 关键事实官方来源覆盖率 100%。
- 无来源数字为 0。
- 核心页面正常收录。
- 每周异常审核量在个人可处理范围内。
- 用户确实使用资格页、日历或比较功能。

## 8. Codex 每次任务的工作方式

### 8.1 开始时

Codex 必须先输出：

1. 当前阶段和本轮明确范围。
2. 已读取的仓库指令和相关文档。
3. 当前仓库状态和已存在实现。
4. 准备修改的模块。
5. 本轮验收命令。
6. 已识别的阻塞或风险。

不需要等待确认的情况：范围明确、操作可逆且不涉及生产写入时，可以继续实现。

必须停下确认的情况：

- 需要生产密钥或生产数据权限。
- 需要选择域名、云平台、付费服务或认证提供商。
- 需求文档之间存在实质冲突。
- 需要删除、覆盖或大规模迁移已有数据。
- 需要扩大到当前阶段以外的资格或功能。
- 无法确认某个来源是否为官方来源。

### 8.2 实现时

- 小步提交，每个变更服务于当前阶段的验收项。
- 优先完成数据契约和测试，再完成页面外观。
- 复用既有组件和模式，避免平行实现同一概念。
- 所有动态事实通过统一数据层读取。
- 任何临时假数据必须显式标注，并与生产路径隔离。
- 不修复与当前范围无关的问题；可以在交付说明中记录。

### 8.3 结束时

Codex 必须按以下格式交付：

```markdown
## 本轮结果

- 完成了什么
- 没有完成什么

## 变更文件

- 文件路径：用途

## 数据库与接口变化

- migration
- schema/API 契约
- 兼容性说明

## 验证证据

- 命令：结果
- 测试：通过数/失败数
- 构建：结果

## 风险与剩余问题

- 阻塞项
- 非阻塞待办

## 下一轮建议

- 仅列出下一个可验收任务
```

不得只回复“已完成”而不提供测试和构建结果。

## 9. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

- 代码、schema、配置和文档保持一致。
- 新增逻辑有对应测试。
- Lint、类型检查、单元测试和相关构建通过。
- 数据库迁移可从干净数据库运行。
- 没有把凭据写入仓库。
- 没有将未验证事实暴露给公开 API 或页面。
- 错误路径、空状态和重试路径已处理。
- 对用户可见的日文文本符合术语规则。
- README 或相关运行文档已更新。
- 交付说明列出验证命令和真实结果。

## 10. 最低安全与质量门槛

### 10.1 安全

- 来源域名白名单与重定向目标校验，阻止 SSRF。
- 采集器默认不执行第三方脚本。
- Playwright 仅用于明确需要的动态页面，并在隔离环境运行。
- PDF 设置大小、MIME 类型和下载超时限制。
- 管理后台必须认证，生产环境不得保留开发后门。
- API 限速，后台写接口不得公开匿名访问。
- 日志不得包含密钥、Cookie、完整认证头或个人敏感信息。

### 10.2 数据质量

- 关键事实来源覆盖率 100%。
- 已发布高风险未验证事实为 0。
- 无来源数字为 0。
- 日期和星期错误为 0。
- 未处理来源冲突为 0。
- 采集器失败不得改变正式事实。

### 10.3 前端质量

- 移动端核心页面和控件可用。
- 状态不能只靠颜色表达。
- 图表有表格或文字替代。
- 重要日期、官方链接、ICS 和比较控件附近不得放广告。
- 广告脚本失败不得影响正文和核心操作。

## 14. 最终交接结论

《日本资格考试数据媒体_完整产品设计方案.md》可以直接作为 Codex 的需求基线，但必须配合本交接说明按阶段执行。

第一轮只启动阶段 0。阶段 0 的目标不是做出完整网站，而是证明项目具备正确的数据契约、权限链、版本模型、测试和可运行骨架。只有这个基础验收通过，才进入宅建与 ITパスポート的数据闭环，再扩展到 6 个资格、SEO 和 AdSense。

整个开发过程中始终遵守一条最高优先级规则：

> 未绑定官方来源与原始快照、未通过规定校验和审核的动态事实，不得出现在公开 API、页面、日历、比较结果或统计数据中。
