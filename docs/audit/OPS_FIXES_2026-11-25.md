## 1. 巡检抓取改到开发机

生产首次巡检（2026-11-25 05:47Z）16 条 `failed` 全部落在 jafp（6）、kinzai（7）、gyoseishoshi（3），错误是 `Connection reset by peer` ×6 与 `timed out` ×10。同一批 URL 在开发机 curl 全部 200（65 KB 级页面），生产仍是 5xx 自由。结论：**生产云出口对这几个站点被限/被重置**，不是来源坏了。若继续在生产抓取，这 16 条会一直被记成连续失败，最终把真实故障淹没。

因此巡检抓取默认改到开发机执行，生产只接收产物：

```bash
PATROL_LIVE_AUTHORIZED=1 PYTHONIOENCODING=utf-8 \
  PYTHONPATH="services/collector/src;services/parser/src" pnpm patrol:sources
pnpm patrol:sync -- --snapshots
```

新增 `scripts/patrol-sync.mjs`（`pnpm patrol:sync`）：校验本机三份产物齐全，把报告里 `snapshot_path` 在传输副本中改写成仓库相对 POSIX 路径（本地报告不动，落库仍按本机路径校验哈希），再 scp `patrol-report.json`／`registry.json`／`cache.json` 到 `/opt/jpqm/var/patrol/`；`--snapshots` 额外同步 `var/official-snapshots/<qual>/`。首次同步后生产 `/opt/jpqm/var/official-snapshots` 共 16 MB（bookkeeping／bookkeeping-preserved-before-F／-F2／fp／fp-kinzai-pre-capture-20261112／fp-preserved／fundamental-it／gyoseishoshi／it-passport／takken）。

本机运行 `patrol-20261125T060035Z`：171 s，61 条登记来源 **changed 45 + unchanged 16**、`failed 0`；报告另保留 2 条 2026-11-11 的失效 capture-only 记录（`capture-only:fp:kinzai-fp-faq`、`source:fp:kinzai-schedule`），它们已不在 registry，落库时按未登记跳过。

## 4. 遗留：29 条到期事实不能靠巡检解决

`staleness` 仍报 `dueFacts 29`（`approvedFacts 1007`、`historicalSkipped 789`、`checked 218`、`sourcesBehindOnSnapshot 4`）。29 条全在 bookkeeping／2026，`fact_key` 是 `payment_deadline_rule` 与 `fee`，`verified_at` 距今 328 天（窗口 90 天）。

这不是数据错乱，是真实欠账：`verified_at` 只在生成 revision 时写入，巡检／落库都不碰事实表。要清掉只能走**三次独立授权**——①采集（对应资格 capture 脚本或 `patrol:sources` 的 changed 来源）→ ②候选入库（`candidate_facts` 新建 pending_review）→ ③审核批准（生成 `fact_revisions` 并更新 `facts.current_revision_id`）。第三步会改动**已发布的公开事实**，必须所有者逐次明示，本轮未执行。

`sourcesBehindOnSnapshot 4` 是同一口径的提示级项（登记来源有更新但快照滞后），随下次抓取与落库自然收敛。
