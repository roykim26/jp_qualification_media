## 1. 为什么观测这一项

Sprint 3A 的 Task C 分析了 `/pass-rate/` 的一个可用性缺口：这个聚合页用 `Promise.all` 并发拉取 6 个资格，**任何一个资格失败都会让整页 503**。当时给出了两个方案：

- **方案 A**：保持整页 503（不改）。
- **方案 B**：`Promise.allSettled`，成功的资格正常显示、失败的资格显示「暫くご利用いただけません」，页面返回 200。

Owner 在 3A 决策时选择了**方案 A**，并在 `docs/audit/SPRINT_3A_REPORT_2026-11-24.md:335` 留下一个**明确的触发条件**：

> 如果生产观测到 `/pass-rate/` 的 503 中，**超过一半**由「单资格故障」而非「API 整体不可用」引起，那么方案 A 的成本（整页不可用）就开始超过方案 B 的成本（索引污染风险），届时应切到方案 B。

这份报告就是去取这个触发条件所需的分母：**`/pass-rate/` 到底有没有 503，503 有多少，其中多少是单资格故障引起的。**

3A 报告 `:504` 还记了一条配套的缺口：

> 当前没有指标区分「API 整体不可用」与「单资格故障」，而 §7.5 的触发条件依赖这个区分。

所以本次观测除了看 503 数量，也一并记录**能否区分**这件事。

## 2. 数据来源与方法

- **来源**：VPS `/opt/jpqm/deploy/caddy-logs/access.log`（Caddy JSON 访问日志，宿主机上的 bind mount）。
- **窗口**：`2026-11-14T11:29:20Z` – `2026-11-25T09:00:04Z`，**10.90 天**。
- **文件**：`10241835` 字节 / `8176` 行。
- **方法**：`grep` + `awk` 按 `"status":` 与 `"uri":` 计数。日志是每行一个 JSON 对象，`ts` 是**数字**（如 `1795597204.8943276`），不是字符串。

> 取数过程中我犯过两个错，都影响过第一版结论，记在这里避免下次重犯：
>
> 1. 第一次用 `match($0, /"ts":"[^"]*"/)` 取时间戳，**一条都取不到**——因为 `ts` 是数字。正则必须是 `/"ts":[0-9]+(\.[0-9]+)?/`。
> 2. 用 `date -d "$START"` 换算部署起点时，把去掉 `Z` 的 UTC 字符串按**本地时区（+08:00）**解释了，导致部署起点被算早 8 小时。必须用 `date -u -d "$RAW" +%s` 且保留 `Z`。

## 4. 结论

**触发条件不成立，而且不是「勉强不成立」，是分母为零。**

3A 的触发条件是「`/pass-rate/` 的 503 中超过一半由单资格故障引起」。生产 10.90 天里：

- `/pass-rate/` 索引页 **503 次数 = 0**；
- 六个章节页 412 次请求 **503 次数 = 0**；
- 全站 5xx **= 0**。

**没有 503，就没有「503 的构成」，触发条件无从谈起。方案 A 不需要重新评估。**

同时也要说清这份结论**不能**证明什么：

- 它不能证明方案 A 在故障发生时是安全的。它只证明**这 10.9 天里没有发生那个故障**。
- 上游 API 在这段时间内没有出现过「单资格失败而其余成功」的情形。这个情形本身在 3A 里是**实测复现过的**（手工让 `fp` 失败，整页 503），所以它是真实的、只是没有在生产自然发生。

### 5.3 无法区分「单资格故障」与「API 整体不可用」

3A 报告 `:504` 指出需要一个能区分两者的指标。**现在仍然没有。** 本次观测只能回答「有没有 503」，不能回答「如果有，是哪种」。原因是日志里 503 的响应体不进 access log（Caddy 只记状态码、uri、时长），而区分两者所需的「哪个资格失败了」只存在于应用日志里。

真要落地这个指标，最小改法是让 `/pass-rate/` 的 503 分支在**响应头**里带一个失败计数（如 `x-upstream-failed: 1/6`），这样 access log 就能直接聚合。但这属于新功能，不在本轮范围。

## 6. 顺带发现

### 6.1 admin 后台的 `HEAD` 返回 404

`deploy-admin-1` 是 15:40 那次部署新增的服务。暴露面核对结果：

| 检查                         | 结果                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `GET /admin`                 | 308 → `/admin/`                                                                                                                |
| `GET /admin/`                | **401**（HTTP Basic 挑战）                                                                                                     |
| `GET /admin/` 带错误口令     | **401**（鉴权真的在生效）                                                                                                      |
| `HEAD /admin/`               | **404**                                                                                                                        |
| `HEAD /pass-rate/`（对照）   | 200                                                                                                                            |
| `docker port deploy-admin-1` | 空（未发布端口，只经 Caddy 反代）                                                                                              |
| 响应头                       | `x-robots-tag: noindex, nofollow`、`x-frame-options: DENY`、`x-content-type-options: nosniff`、`cache-control: no-store`、HSTS |

`HEAD` 的 404 是 `apps/admin/src/server.ts` 的方法分派缺口：路由只判 `GET`（`:663`/`:676`/`:697`）与 `POST`（`:705`/`:726`/`:746`），`HEAD` 落到末尾 `:765` 的 `send(res, 404, 'not found', …)`。

**风险评级：低。** `HEAD` 不返回任何内容，所以它不会泄露数据，反而比 `GET` 更不暴露。但这是一个「方法不支持」而非「故意拒绝」的响应，会让自动化探测把 admin 判成「不存在」，与真实状态（存在且需要鉴权）不符。**未修，记入 §8。**

### 6.2 `/ready` 仍然没有外部暴露

`GET /ready` → **404**。这是 3D 的刻意决策（不在 Caddy 暴露 `/ready`，避免泄露内部状态、避免依赖链把 DB 抖动放大成整站下线），**没有被 15:40 那次部署破坏**。

### 6.3 Caddy 日志轮转仍未触发（不是失效）

`deploy/caddy-logs/` 里只有 `access.log`（10242952 B）与 `blog-access.log`（600740 B），**没有轮转产物**。`roll_size 10mb` = `10485760` B，而当前 `10242952 < 10485760` —— **阈值还没到，不是轮转坏了**。

（这条判断我在 3A–3M 部署报告里写错过一次，当时把「还没到阈值」当成了「轮转失效」。判断一个机制失效之前，先确认它的触发条件是否满足。）

## 9. 下一步建议

1. **P1 — 继续观测，不急着改方案 A。** 触发条件的分母是 0，任何「切方案 B」的动议现在都没有数据支撑。等 `/pass-rate/` 的 503 累计到有意义数量（比如 ≥10 次）再回来看构成。
2. **P2 — 让 503 可区分。** 在 `/pass-rate/` 的 503 分支加 `x-upstream-failed: <failed>/<total>` 响应头。这是让 3A 的触发条件从「一句话」变成「可计算的指标」的最小改动，且不改变任何行为。
3. **P3 — 给 admin 的 `HEAD` 补一个处理**（返回与 `GET` 相同的状态码、不带 body）。低危，但能让探测结果与真实状态一致。

5. **P3 — 补 `/shikaku/:slug/pass-rate/` 的 `?sort=` 测试**（§7 第 4 条）。
